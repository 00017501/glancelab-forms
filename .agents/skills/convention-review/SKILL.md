Review the change as a senior reviewer of this app. Enforce the conventions documented in this repo - do **not** invent rules from generic best practice. The conventions docs are the source of truth.

This is a research tool. Two things matter beyond ordinary correctness: the promises made to participants in the consent text, and the validity of the measurements. A bug in either can make the whole study unusable.

## Review Process

Work in this order. Do not skip steps.

### 1. Gather context

Choose and report the scope before reviewing. Run the bundled helper from the repository root:

```bash
# Staged, unstaged, and untracked non-ignored files.
uv run --project backend python .agents/skills/convention-review/scripts/review_checks.py

# Committed branch changes plus local changes; main is this repo's integration branch.
uv run --project backend python .agents/skills/convention-review/scripts/review_checks.py --base main
```

For a PR, pass its explicit locally available base ref (for example `origin/main`); the helper
uses the merge base and never fetches or guesses a ref. If the ref is missing, report the
failure and resolve the intended base before reviewing. The default intentionally excludes
already committed branch changes. An empty scope is not a review of the latest commit.

Inspect `git diff --cached` and `git diff` for local changes, read untracked files in full,
and for branch review inspect `git diff <reported-merge-base> HEAD`. Read deleted files from
the relevant Git revision. Never substitute commit titles for a diff. Identify what the change
was asked to do (the user's request, the plan, or the PR description) and how the files connect.

### 1.5 Classify the change

Map what changed to the extra review depth it requires. The classification surfaces in the final report so readers see why the review loaded the context it loaded.

| What changed | Implication |
| --- | --- |
| Consent step, session creation, withdrawal, deletion | Read [`privacy.md`](../../rules/privacy.md) in full. No row before consent; "I don't agree" writes nothing; withdrawal and admin deletion are hard deletes; consent time and text version are stored; the consent step cannot be removed or moved. |
| Anything that logs, any middleware, `Caddyfile`, `docker-compose.yml`, uvicorn flags | No IP address reaches a log, table or export. Access logs stay off. Only the in-memory login limiter may read the client address. |
| Participant runtime (`frontend/participant/`) | Nothing loads from another origin. Images are preloaded. Reaction time starts at the painted frame. Coordinates are normalised to the displayed image. The stimulus fits the viewport. The server is told a timed step started before it renders. Preview writes nothing. |
| Session progress, step results, resume logic | A timed step that was started and not finished is marked interrupted and skipped, never replayed. The session is flagged. Check the refresh and Back paths, not only the forward path. |
| Variant assignment | Counts are read and the session inserted in one immediate transaction. Counted: completed plus recently active. Tie-break is random. There is a test with concurrent starts. |
| Form editing API or editor UI | A published form accepts text changes only; the backend enforces it and the UI mirrors it. Duplicate copies structure, never responses. |
| Step types (`schemas/steps.py`, plugins, editor cards) | All five parts move together: config schema, participant plugin, editor card, CSV columns, tests. |
| Export and responses table | One row per session. Only the fields allowed by `privacy.md`. Column names and order are stable for the same form structure. Multi-select and "Other" values are unambiguous. |
| Admin routes and auth | The router carries `require_admin`. Cookie flags are set. Login is rate limited in memory. Nothing returns or logs the credentials. |
| Image upload and storage | Type and size are validated by decoding, metadata is stripped, large images are resized. Keys are server-generated. Bytes are served through the backend. An image in use cannot be deleted. |
| Participant-facing API responses | Only the assigned variant's data is returned. No other variant, target box or variant list leaks. |
| Models or migrations | A model change has an autogenerated, hand-read Alembic revision in batch mode. No applied revision is edited. |
| Admin UI | shadcn/ui components and dnd-kit, tokens from `DESIGN.md`, confirmations on destructive actions, plain wording for a non-technical user. |
| Dependencies (`pyproject.toml`, `package.json`) | Each addition is justified and does not phone home. A new service in `docker-compose.yml` needs an ADR. |

If nothing matched, proceed straight to Step 2.

### 2. Report mechanical checks

The helper runs Ruff lint, Ruff format-check and Pyright on changed Python files under `backend/`,
and `npm run typecheck` and `npm run lint` in each frontend app that has changed files. It does
not rewrite files. Deleted paths remain in the review scope.

Report each check as **passed**, **failed**, **unavailable**, or **not applicable**, preserving
its diagnostics and exit status. A nonzero helper result must not be described as clean.
An unavailable tool is a blocked check, not a pass. Keep one short tooling summary and avoid
repeating its diagnostics as individual review findings.

If the change touches behaviour, also run `uv run pytest` in `backend/` and report it the same way.

### 3. Discover and read project conventions

Don't assume which convention docs exist - discover them.

```bash
ls AGENTS.md PRODUCT.md DESIGN.md .agents/rules/ docs/adr/ 2>/dev/null
```

Sources of truth (read whichever are present):

- **`AGENTS.md`** - what the product is, the privacy invariants, product rules, definition of done.
- **`.agents/rules/*.md`** - the convention set. Read every rule whose `paths:` match the changed files.
- **`PRODUCT.md` / `DESIGN.md`** - the design direction for admin UI changes.
- **`docs/adr/`** - recorded decisions.

If no convention doc covers a point, fall back to widely-accepted practice - but say explicitly that you are applying a conventional default, not a project rule, and lower your confidence accordingly.

### 4. Read surrounding code

Don't review the diff in isolation. Read the full file, the imports, and at least one call site. If the change deviates from how similar code in this repo is written, that deviation is itself a finding.

### 5. Review the diff

Walk the changes against the convention docs and what the change was asked to do. Apply confidence-based filtering (below). Group findings by severity.

### 6. Report findings

Use the output format below.

---

## Confidence-Based Filtering

- **Report** only issues you are >80% confident are real problems.
- **Skip** anything the tools already flagged - point at the tool summary instead.
- **Skip** stylistic preferences unless they violate documented conventions.
- **Skip** issues in unchanged code unless they are CRITICAL.
- **Consolidate** similar issues into one finding.
- **Prefer concrete violations** of documented conventions over abstract concerns.

---

## Severity Framework

Use the conventions docs to decide _what_ is a violation. Use [the severity criteria](references/severity.md) to decide _how serious_ it is; read them before assigning findings. CRITICAL means
security, privacy or data-loss risk and blocks merge; HIGH means study validity, architecture or
data integrity; MEDIUM covers quality and testability; LOW is optional polish.

---

## AI-Generated Code Addendum

When reviewing AI-generated changes, apply these extra checks.

- **Phantom imports / phantom APIs** - invented module paths, function names or kwargs. Verify against the installed version, especially for jsPsych plugins and shadcn/ui components.
- **Speculative abstractions** - factories, registries or base classes for a single implementation. This app is small on purpose.
- **Scope creep** - multiple admins, i18n, charts, analytics, tracking. `AGENTS.md` rules these out.
- **Pattern drift** - a pattern unfamiliar to this codebase. Match the surrounding code.
- **Over-broad exception handling** - `except Exception` to look robust. It hides real bugs.
- **Plausible but invented defaults** - timeouts, durations and limits chosen from nothing; check whether a setting or an agreed value exists.
- **Convincing comments that misstate the why** - verify against the rules and ADRs.
- **Cost / complexity escalation** - an extra service, cache or queue with no measured need.

The "explain it" test: can the submitter defend every line? If the answer is "the AI wrote it that way," the line is not ready.

---

## Output Format

For each finding:

```
[SEVERITY] Short title
File: path/to/file.py:LINE
Convention: <which doc/section this violates, or "general practice" if no project doc applies>
Issue: One or two sentences.
Fix: What to change, with a minimal code example if useful.
```

End with a summary:

```
## Review Summary

Change: <what it was asked to do> - done / not done (list what is missing)
Classification: <rows matched in step 1.5>
Tooling: <one-line summary of Ruff, Pyright, pytest and frontend check results>

| Severity | Count | Status |
| --- | --- | --- |
| CRITICAL | 0 | pass |
| HIGH | 2 | warn |
| MEDIUM | 3 | info |
| LOW | 1 | note |

Verdict: WARNING - 2 HIGH issues should be resolved before merge.
```

## Approval Criteria

- **Approve**: No CRITICAL or HIGH issues; required checks passed; the change does what was asked.
- **Warning**: HIGH issues present - discuss before merging.
- **Block**: CRITICAL issues - must fix before merge.

---

## The Discipline

1. **Tooling first.** Run the configured checks and cite their output.
2. **Conventions are the source of truth.** If it is not in the conventions or an ADR, it is a suggestion - flag it, but don't block on it.
3. **Match the codebase.** Patterns that conflict with existing project style are wrong by default.
4. **Filter aggressively.** A flood of low-confidence findings trains readers to ignore the review.
5. **Be specific.** Every finding cites a file, line, and which convention it violates.
